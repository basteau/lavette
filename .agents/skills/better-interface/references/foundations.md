# Foundations

Read once per task. These principles govern the collection; domain skills own the details.

## Order of judgment

Honor the user's task, accessibility needs, platform conventions, and established identity before applying defaults. Requirements outrank preferences. Preserve a coherent existing system; replace it only within the requested scope.

**Clarity and coherence, without erasing character.** Identify what must survive before simplifying. Restraint removes competing decisions, not necessary information, capability, or expression. A small decision budget constrains exploration; meeting its counts does not establish quality.

## Few, purposeful choices

Reuse coherent roles and relationships. Where the system is missing or inconsistent, start with the fewest distinctions that explain the content and behavior; domain skills own their defaults. Develop one expressive idea first when the brief calls for it. Add distinction for a task, content, access, platform, or identity need—not a stylistic quota.

## Work and judge in context

Work in the medium provided: source, a running product, a design file, or a specification. Use existing tools and components; no framework, library, rendering technology, or color notation is required.

Inspect representative content and states. When tuning is warranted, name the uncertainty and expose only the few parameters that can resolve it—not the whole design system. Compare one bounded change with the original in the actual task, seeking human judgment when subjective fit is consequential. Change one dimension at a time, retain the better result, and commit it to the existing source of truth. Without direct inspection or feedback sufficient to resolve the uncertainty, mark the choice provisional. No tuning panel is required.

Evidence limits the claim: a screenshot supports visual observations, not verified behavior. Separate observed problems, hypotheses, and checks not performed. Never claim accessibility conformance or usability improvement from appearance alone.

“Done” clauses are internal checks, not output requirements. Check what is relevant to the requested scope and affected behavior. Give one consolidated report of findings or changes, meaningful verification, and consequential limitations; omit unchanged defaults and checklist transcripts.

Stop when the selected problem is resolved or no justified change is found, relevant checks reveal no new blocker, and another pass would express preference rather than address evidence. Keep the original when the alternative is not better supported by the brief. If verification is unavailable, report the unresolved check rather than continuing speculative polish. Passing checks supports specific claims; it does not establish taste.
